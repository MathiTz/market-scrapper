# Audit: security, reliability, observability, dead code — September 2026

Scope: the whole repo (`scraping/`, `api/`, `web/`), checked against what is actually there, not assumed.
Ordered by what would hurt most if left alone. Nothing here has been fixed - this is a findings list to
pick from, the same way `docs/plans/promotion-availability-by-branch.md` is a plan rather than a diff.

## Audit logs, specifically (the question that started this)

You're right that there is no audit log in the usual sense - no record of who changed what, when, in the
admin sense. But there **is** a scrape-run log already: `models/scrape_attempt.py`'s `ScrapeAttempt` table
records `site_key`, `success`, `error`, `items_found`, `duration_ms` and `run_id` for every scrape, and
`local_api/app.py`'s `/scrape/status` route already reads it back. It is just never surfaced anywhere a
person looks - no page in the UI shows it, nothing alerts on a run of failures. That is real, low-effort,
already-collected data going unused before any new logging is built.

What is genuinely missing: no record of admin/write actions (there are none reachable in production - see
below), and no error tracking / APM anywhere. A failure in the deployed Worker is visible only via
`console.error`, in Wrangler's own log tail, which nobody is watching; a scraper failure lands in
`ScrapeAttempt.error` with nothing paging anyone about it.

## Dead code: the admin page calls an endpoint that does not exist

`web/components/admin.tsx` calls `fetch("/api/admin", { method: "POST" })` on load and on save. That route
is not implemented anywhere: `api/src/app.ts` (production) has no `/api/admin` - it would 404 through the
`app.all("/api/*", ...)` catch-all - and `scraping/local_api/app.py` (local dev) has no such route either.
`/admin` is a real, reachable page (`app/main.tsx` routes it), rendering a form that always fails silently.
It is dead weight in the shipped bundle and a trap for whoever next assumes it works because the page loads
fine. Either build the backend for it or remove the page and the route until it is worth building.

## Security

- **No rate limiting on `/api/location` / `/api/location/reverse`** (`api/src/app.ts`). Input length is
  bounded (`MIN_QUERY`/`MAX_QUERY` in `geocoding.ts`) and identical queries are edge-cached for 24 h
  (`cf: { cacheTtl, cacheEverything }`), but a client varying its query text on every request bypasses that
  cache entirely and can drive unbounded traffic to Photon (the upstream OSM geocoder) through our Worker,
  on our IP's reputation. Low cost at today's traffic; worth a Cloudflare rate-limiting rule before it isn't.
- **Unsafe-by-default local dev config** (`scraping/config.py`): `DEBUG` defaults to `true` and `HOST`
  defaults to `0.0.0.0`; `SECRET_KEY` defaults to `"dev-secret"`. Fine as long as `local_api/app.py` only
  ever runs on a laptop, which is the intent - but the *defaults* are unsafe rather than safe, so a forgotten
  override is the difference between "only reachable on localhost" and "Werkzeug's debugger reachable on the
  network, with everything that implies." Flipping the defaults (safe unless explicitly opted out) costs
  nothing and removes the footgun.
- **Clean**: no secrets committed (`git ls-files` sweep for connection strings/API-key patterns found only
  `.env.example`'s placeholder and README's documented format); `.env`/`market.db` are properly gitignored;
  the production API is read-only (`/api/public` GET, `/api/location` is a search proxy, not a write, `/api/
  session` is an explicit 501 stub); no SQL-injection surface (SQLAlchemy ORM throughout, parameterized raw
  SQL in `services/publish.py`); `npm audit` reports 0 vulnerabilities in both `web/` and `api/`.

## Reliability

- **Scheduler still has no misfire handling** (`scheduler.py`'s `CronTrigger`): no `misfire_grace_time`, no
  `coalesce`. A laptop asleep through 6:00 or 12:00 silently skips that run, with no retry and no alert. This
  was flagged in an earlier session and never fixed.
- **No CI.** `.github/workflows` does not exist. Every `npm test` / `python -m unittest` / typecheck run this
  project has had has been a person (or me) running it by hand, before a manual `./release.sh` or `npm run
  deploy`. Nothing stops an untested change from reaching production; the only thing enforcing quality right
  now is discipline, not infrastructure.

## Performance

- **The 500 kB chunk-size warning has appeared on every single build this session** and has never been
  acted on. Two concrete, safe things already sitting in the bundle for free: `components/vitrine.tsx` (the
  design-system showcase, gated to `/demo?vitrine=1`, never shown on `/`) and `components/admin.tsx` (see
  "dead code" above) could both be dynamically `import()`-ed instead of bundled unconditionally, so a real
  shopper's first load never pays for either.

## Loose ends from recent work (not new, just collecting them in one place)

- `docs/plans/promotion-availability-by-branch.md` - written, not built.
- `scraping/services/image_enrichment.py` / `backfill_images.py` / their tests - written (17 tests pass),
  never reviewed, wired, or committed; still sitting untracked in the working tree.
- `web/docs/VALIDACAO.md` (from the merged UX-audit PR) already documents its own gaps: physical-device,
  Firefox, and real screen-reader testing are explicitly listed as not done.

## What I'd do first, if picking three

1. Rate-limit `/api/location` (cheapest fix, closes an open-ended cost/abuse surface).
2. Remove or actually build `/api/admin` - a page that silently fails is worse than no page.
3. Add `misfire_grace_time`/`coalesce` to the scheduler - a few lines, closes a known data-freshness gap.
